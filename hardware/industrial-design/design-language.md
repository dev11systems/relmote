# Relmote design language

## Character

Relmote should read visually as:

> **a trustworthy little field computer / interface instrument**

—not as a luxury phone, surveillance device, gamer accessory, or mysterious black box.

## Principles

### State should be legible

A person should be able to glance at the device and understand:

- Is it powered?
- Is it armed?
- What is it connected to?
- What path is active?
- Is it performing output?
- Has STOP been latched?

### Physical controls outrank touch UI

AUTHORIZE and STOP should remain physical.

A touchscreen, if ever added, must not become the sole safety interface.

### Tactile differentiation

AUTHORIZE and STOP should differ in:

- location;
- shape;
- texture;
- required motion/force.

Color may reinforce this but must never be the only distinction.

### Labels should survive

Prefer:

- molded/engraved labels;
- etched legends;
- replaceable front/rear plates.

Avoid relying entirely on ink that disappears after years of pocket wear.

### Thickness is allowed

The project should not chase thinness for its own sake.

Thickness buys:

- repairability;
- battery serviceability;
- stronger ports;
- thermal headroom;
- module mechanics;
- physical buttons.

### Honest construction

Visible screws and service seams are acceptable.

A repairable seam is preferable to a glued “seamless” object.

### Modules should look integrated but removable

A snapped module should feel like part of the device while clearly remaining a distinct replaceable object.

Mechanical affordances should communicate where to grip/remove it.

### No accidental stealth

When target output is armed or active, the physical device should show it.

There is no design objective to make an operating Relmote visually indistinguishable from a passive charger.

## Suggested materials

To investigate:

- glass-filled or impact-modified engineering polymer shells;
- aluminum or magnesium internal midframe where needed;
- replaceable polymer rear/module rails;
- silicone/TPE feet or grip strips only where replaceable.

Avoid rubberized coatings that become sticky with age.

## Fasteners

Aim for:

- one or two standard screw types per device;
- common driver sizes;
- documented torque;
- no security screws solely to deter owners.

## Accessibility

- status should not depend only on color;
- controls should be distinguishable by touch;
- type should be readable at arm's length where practical;
- UI should tolerate motion/low-light/high-glare contexts;
- beeps/haptics should supplement rather than replace visual state.
